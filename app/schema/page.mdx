# Data schema

<Lead>A `schema` declares the output dataset: each field's **type**, **domain**, and creation default. It is the source of truth for a field's scale, so a chart resolves scales, draws axes, and mints data with **zero starter data**. `structure` says how many tables that dataset has — one by default, or a network of nodes and links.</Lead>

<Section id="structure" title="How many tables">

`structure` says which tables the dataset has. Leave it out and you get one, whose columns are the schema itself:

```js
schema: {
  age: { type: "quantitative", domain: [18, 80] },
  belief: { type: "quantitative", domain: [0, 1] },
}
```

`structure: "network"` gives two tables under `tables`, filling the roles `nodes` and `links`. Each has its own columns, so a node and a link both carry their own attributes.

```js
schema: {
  structure: "network",
  tables: {
    nodes: {
      id: { type: "categorical", key: true, open: true },
      x: { type: "quantitative", domain: [0, 100] },
      y: { type: "quantitative", domain: [0, 100] },
    },
    links: {
      source: { type: "ref" },
      target: { type: "ref" },
    },
  },
}
```

`data` is keyed by table name, and so are `getData()`, `onChange` and `setData`. Omit a table and it starts empty.

Give a table a `role` to name it for your data — `claims` and `supports` rather than `nodes` and `links`. Marks and edits find their table by role, so nothing else in the spec changes. See [Network](/marks/network) for the marks and gestures that draw one.

The links table also takes `directed`, which says whether `source` → `target` is ordered:

```js
links: {
  role: "links",
  directed: true,
  fields: { source: { type: "ref" }, target: { type: "ref" } },
}
```

`true` draws arrowheads and separates reciprocal links; `false` treats the pair as unordered, so `connect` refuses `b → a` once `a → b` exists. Leave it out and neither applies. See [Directed or undirected](/marks/network#directed).

</Section>

<Section id="ref" title="Keys and references">

Two field declarations join one table to another. `key: true` marks the column that identifies a row. `type: "ref"` marks a column that names one.

A `ref` has no `domain` of its own — it reads the key column's, so you never list identities twice. A value that names no row is reported when you seed it, and dropped when it becomes dangling: delete a node and its links go with it.

Pair `key` with `open: true` so a creating edit can mint a fresh identity automatically. Naming is a separate act: put `editText()` on a `text` mark and write the label in place.

A closed `domain` on a key is a fixed roster. `create` hands out the declared values one at a time and refuses once they run out — that caps how many rows may exist.

None of this needs a network. A single table can declare a `key` too, and every row you create gets an identity:

<Section id="table" title="Which table a mark draws">

Every mark draws exactly one table, and takes a `table` option naming which. On a single-table chart there is nothing to say, so you never write it.

With no `table`, a mark draws the **primary** table: the only one on a `structure: "table"` chart, and the nodes on a network. `link()` is the exception — it draws the links.

Use `table` when you want an ordinary mark over another table:

```js
barY({ table: "links", channels: { x: { field: "source" }, y: { field: "strength" } } })
```

An edit on that mark writes rows of that table, and `getData()` shows the change there. A name the schema does not declare is reported, and the mark falls back to the primary table.

Positional scales are shared across the chart. Two tables encoding different kinds of field on the same axis will disagree about its type, which is reported — give the second mark its own chart instead.
