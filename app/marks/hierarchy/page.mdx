# Hierarchy

<Lead>A **hierarchy** is nodes that sit inside each other, declared with `structure: "hierarchy"`. The nodes are one table and each "this is inside that" is a row of a second, `nesting`. Any mark that draws a node shape can draw a container: a `contains` channel says which rows hold others, and `fit: true` on a size channel makes a container follow its contents. `edit.hierarchy.nest` drops a node into a container or out of one.</Lead>

<ApiReference entries={api} />

<Section id="schema" title="Declaring the structure">

`structure: "hierarchy"` gives the dataset a `nodes` table and a `nesting` table. A `links` table is optional.

```js
schema: {
  structure: "hierarchy",
  tables: {
    nodes: {
      id: { type: "categorical", key: true, open: true },
      kind: { type: "categorical", domain: ["group", "note"] },
      x: { type: "quantitative", domain: [0, 100] },
      y: { type: "quantitative", domain: [0, 100] },
      w: { type: "quantitative", domain: [0, 600] },
      h: { type: "quantitative", domain: [0, 400] },
    },
    nesting: {
      child: { type: "ref" },
      parent: { type: "ref" },
    },
  },
}
```

`getData()`, `onChange` and `setData` use one array per table. A table you leave out of `data` starts empty.

<Section id="nesting" title="The nesting table">

The nesting table is declared like any other table: a field map, with a type for every column.

It needs two `ref` columns. The first names the contained node and the second names its container. Both point at the nodes table's `key: true` column, so their values are node identities. The column names are yours.

```js
nesting: {
  child: { type: "ref" },    // the contained node
  parent: { type: "ref" },   // its container
}
```

One row is one membership. A node with no row is at the top level. A node has one container at most, and is never inside itself or its own contents. A seeded row that breaks either rule is ignored with a warning, and so is a row that names a missing node.

Add any other columns you want to record about a membership. They take a `type`, a `domain` and a `default` like columns anywhere else. A row made by a drop takes each column's `default`, or the value you pass in `edit.hierarchy.nest({ defaults })`.

```js
nesting: {
  child: { type: "ref" },
  parent: { type: "ref" },
  coder: { type: "categorical", domain: ["seed", "participant"], default: "participant" },
}
```

Deleting a node removes the nesting rows that name it. Its contents move to the top level.

</Section>

<Section id="naming" title="Naming the tables">

Name the tables for your data and give each a `role`: `"nodes"`, `"nesting"` or `"links"`. A table named after its role needs no `role`, which is the short form used above.

```js
tables: {
  topics:      { role: "nodes",   fields: { … } },
  memberships: { role: "nesting", fields: { … } },
}
```

`data`, `getData()` and `setData` are then keyed `topics` and `memberships`. Marks and edits find each table by its role.

<Section id="containers" title="Containers">

A container is a row of an ordinary mark. Two statements in the channel map set it up.

`contains` says which rows hold other nodes. `{ value: true }` is every row. `{ fn }` or `{ field }` decides per row, so a chart can let groups receive and notes not.

`fit: true` on a size channel says the column follows the row's contents. It applies to rows that hold other nodes. The channel names a `field`, and the fitted size is written to it.

```js
rect({
  channels: {
    x: { field: "x" },
    y: { field: "y" },
    width: { field: "w", scale: null, fit: true },
    height: { field: "h", scale: null, fit: true },
    contains: { fn: (d) => d.kind === "group", padding: 12 },
  },
})
```

`scale: null` reads the column as pixels. `padding` is the room between a container's edge and its contents; see [Padding and spacing](#spacing).

A row with contents has its fitted columns set for it, so a resize edit leaves them alone. A row without contents keeps its own size and stays editable.

Because the size is in the data, other channels can read it. The examples here place a group's name from its `h` column.

<Section id="spacing" title="Padding and spacing">

Every container keeps `padding` between its edge and its contents. The default is 10px. Give one number, or a side each; a side you leave out takes the default.

```js
contains: { fn: (d) => d.kind === "group", padding: { top: 30, right: 12, bottom: 12, left: 12 } }
```

A fitted container is sized to leave that room. A container with a size of its own moves its contents inside it.

`dodge` keeps nodes from overlapping. It is a channel like `contains`: `true` is every row, and `{ fn }` or `{ field }` picks the rows that take part. `gap` is the space they keep, 8px by default.

```js
dodge: { value: true, gap: 10 }
```

Nodes are compared with their siblings: the contents of one container with each other, and the top-level nodes with each other. When two overlap, the node you just dropped stays put and the other moves the shortest distance that clears it. A container that grows pushes its neighbours the same way, and they take their contents along. A pushed node stays inside its container's padding, or inside the plot at the top level. Where there is no room left, nodes are moved as far apart as the space allows.

Nothing is pushed while you drag. It happens on release, and when data arrives through `setData`. Seeded data is spaced once, at the start. Without `dodge`, nodes stay where they are put.

<Section id="fixed" title="Fixed containers">

Leave `fit` off and a container keeps the size it was given. Use this for regions that are part of the question: buckets, lanes, zones. Lock them with `lock` so only the cards move. Cards stay inside the bucket's padding, and a locked row is never pushed.

The answer is the nesting table: one row per card, naming its bucket.

<Section id="gestures" title="Dragging in and out">

`edit.hierarchy.nest()` goes on the mark you drag, beside `move({ mode: "relative" })`. The move carries the node. On release, the node joins the innermost container under the pointer. Released over no container, it leaves the one it was in.

While you drag, the container the node would join is outlined and drawn at the size it would take. The container it came from holds its size until you let go. Style the outline with the `target` state of `effects`.

Moving a container is the same `move`: its contents travel with it.

A rule about which nodes may go where is a constraint on the nesting table. A drop the rule refuses shows no outline and changes nothing.

<Section id="links" title="Nested and linked">

Add a `links` table and the nodes can be connected as in a [network](/marks/network). `link()` draws the links and meets a container at its edge. A `ports` channel and `edit.network.connect()` work on the same mark.

<Section id="external" title="Reading and setting from outside">

Containment is plain rows, so a program reads and writes it like any other data. `getData()` returns the nesting rows and each container's fitted size.

`setData` takes the same shape. Change the nesting rows and every container re-fits. A node sent with no `x` and `y` is placed inside the container it joins. With `dodge`, it is also moved clear of the nodes already there.

```js
const data = el.getData();
el.setData({ ...data, nesting: [...data.nesting, { child: "n4", parent: "g2" }] });
```
